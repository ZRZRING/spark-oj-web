# Spark OJ Web

本文件用于约束本项目内 AI 代码生成与修改行为，适用于整个仓库。

## 一、编码风格与命名规范

### 1.1 通用风格
- 使用 TypeScript，优先类型安全实现，避免 `any`；确需使用时必须说明原因并缩小作用域。
- TypeScript 代码建议每个独立元素前后保留一个空行分隔，提升可读性。
- 禁止直接引用基础类型作为业务语义类型，优先通过具名类型/别名表达业务含义。
- 保持最小改动原则：只改与需求相关的文件和逻辑，不做无关重构。
- 代码结构简洁，避免重复逻辑；通用能力优先抽取到 `src/utils` 或 `src/stores`。
- 复用现有模式，保持与当前项目风格一致，不引入风格冲突。

### 1.2 Vue 组件与文件命名
- Vue 组件、页面组件采用 `PascalCase`，例如 `HeaderItem.vue`、`ProblemsView.vue`。
- 列表页面使用复数命名（如 `ProblemsView.vue`、`SubmissionsView.vue`）。
- 一级页面放在 `src/views` 根目录；二级及以上页面放在对应子目录，文件名以 `View` 结尾。
- 子路由 path 使用相对写法，不以 `/` 开头。
- 比赛、题目、提交等列表页面遵循复数命名约定（例如 `ContestsView.vue`）。

### 1.3 变量与符号命名
- 变量/函数使用 `camelCase`。
- 类型、接口、枚举成员使用明确语义命名，避免单字母命名（循环索引等临时变量除外）。
- Store 命名采用 `useXxxStore` 形式；状态字段命名应表达业务含义。

## 二、技术栈声明与首选库

### 2.0 本地运行
- 安装依赖：`pnpm i`
- 启动开发环境：`pnpm run dev`

### 2.1 前端技术栈
- 框架：Vue 3（Composition API）
- 构建：Vite
- 语言：TypeScript
- 路由：Vue Router 4
- 状态管理：Pinia
- HTTP：Axios（统一使用 `src/utils/service.ts`）
- UI：Element Plus + `@element-plus/icons-vue`

### 2.2 首选实践
- 网络请求必须通过统一封装发起，不在业务组件里直接创建 axios 实例。
- 权限、登录态与用户信息优先放在 Pinia Store，避免分散在多个页面中。
- 公共常量放在 `src/config`，避免魔法字符串散落。

## 三、需要遵循/避免的架构模式

### 3.1 必须遵循
- 分层清晰：View 负责展示与交互，Store 负责状态与业务动作，Utils 负责通用能力。
- 路由守卫负责页面级访问控制（登录校验、权限校验），页面内部仅保留必要兜底。
- 异步请求必须有错误处理分支，禁止吞错。

### 3.2 明确避免
- 避免在多个组件复制同一业务逻辑（尤其是鉴权判断、接口错误提示）。
- 避免在组件中直接操作 `localStorage` 作为主流程；应优先通过 Store 封装。
- 避免引入未在项目中使用的新状态库/请求库/样式体系。

## 四、安全要求与错误处理

### 4.1 安全要求
- Token 仅通过统一请求拦截器注入 `Authorization`，禁止在各处手写请求头。
- 不在日志、提示信息、代码注释中输出敏感信息（token、完整凭证、密钥等）。
- 涉及后台管理页面时，必须做前端路由权限判断，并以后端返回权限为准。

### 4.2 错误处理
- API 请求失败时返回统一、可读的错误消息，禁止空白失败。
- 对可预期错误（401/403/404/参数错误）给出明确提示；不可预期错误给出通用提示并保留调试信息入口。
- 新增接口调用时，类型定义（请求/响应）需同步补齐到对应 `*_type.ts`。

## 五、文档标准

- 新增或修改接口调用时，需同步更新接口说明与字段语义。
- 业务规则变化（权限、状态流转、路由策略）应在相关文档中留下可追溯记录。
- 文档内容要求：目的、入参、出参、错误场景、前端处理策略。
